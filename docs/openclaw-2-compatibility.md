# OpenClaw 2.0 compatibility assessment

Status: compatibility spike only. This document does not authorize merging,
releasing, or migrating live Knapsack state.

## Recommendation

The upgrade is viable, but it is not a safe mechanical vendor refresh. Target
OpenClaw `2026.8.2` in stages and keep the current `2026.5.22` runtime available
for rollback until the shared-user authorization and migration tests pass.

The first production-capable upgrade should contain only compatibility work.
Adoption of new OpenClaw features should follow in separate pull requests so a
runtime failure can be distinguished from a product behavior change.

## Verified baseline

- Knapsack currently vendors OpenClaw `2026.5.22`.
- The current vendor tree differs from the pristine `2026.5.22` npm package in
  more than 60 runtime files. Seventeen compiled-file customizations are guarded
  by `scripts/clawdbot-patch-manifest.json`.
- Knapsack also adds `dist/knapsack-gateway-entry.js`,
  `dist/knapsack-session-context.js`, bundled Slack and WhatsApp extensions, and
  the `telegram-bot-manager` source tree.
- The pristine `2026.8.2` package expands from roughly 109 MB to 225 MB
  unpacked in the compatibility workspace. Its `dist` directory is roughly
  212 MB versus the current bundle's 187 MB before Knapsack pruning and runtime
  dependency staging.
- An unmodified `2026.8.2` Gateway reached its live signal in 4.2 seconds under
  Node 25.9.0 and 3.4 seconds under Node 22.22.3, using an isolated temporary
  state directory.
- The same Gateway fails immediately under Knapsack's currently bundled Node
  22.19.0. OpenClaw rejects the embedded SQLite 3.50.4 because it is affected by
  an upstream WAL-reset corruption bug. Node 22.22.3 is the minimum supported
  Node 22 release and passed the isolated Gateway smoke test.

## Mandatory compatibility work

### 1. Upgrade the bundled Node runtime first

Change both Node preparation scripts to use `22.22.3` or newer and exercise the
Gateway smoke test with the exact generated binary on macOS and Windows. The
runtime must not be upgraded while leaving release packaging on Node 22.19.0.

### 2. Make vendor installation reproducible

The `2026.8.2` npm package does not ship a package lock. A plain production
`npm install` currently fails peer resolution between Mistral and OpenTelemetry.
The compatibility spike succeeded with `--legacy-peer-deps`, but production
must check in a reviewed shrinkwrap generated by the approved Node/npm toolchain
instead of resolving dependencies during a release build.

### 3. Never run upstream lifecycle or Doctor commands against live state

An isolated smoke command demonstrated that `OPENCLAW_STATE_DIR` alone is not
an isolation boundary. Upstream package cleanup resolves legacy plugin state
from `OPENCLAW_HOME`; without that override it can remove Knapsack's
`plugin-runtime-deps` cache. Compatibility commands must set all of:

- `OPENCLAW_HOME` to a disposable directory;
- `OPENCLAW_STATE_DIR` to a disposable directory;
- `OPENCLAW_CONFIG_PATH` inside that directory; and
- `OPENCLAW_DISABLE_BUNDLED_PLUGIN_POSTINSTALL=1` during package inspection.

The existing Gateway smoke test now establishes these boundaries and accepts
explicit runtime and Node paths for cross-version testing.

### 4. Replace broad `doctor --fix` with a Knapsack-owned migration

On a disposable legacy fixture, Doctor correctly migrated
`openai-codex/gpt-5.5` to `openai/gpt-5.5`, preserved Codex runtime intent, and
removed the stale OpenProse entry. It also made unrelated changes: it created a
canonical agent, disabled unavailable skills, created heartbeat configuration,
rebuilt plugin state, and emitted host-level findings.

Knapsack should therefore implement and test the exact config/session changes
it requires. Doctor can be run as a read-only diagnostic afterward; it must not
be the desktop application's implicit live-state migration mechanism.

### 5. Port custom behavior away from hashed compiled chunks

OpenClaw 2.0 changes content-hashed chunk names, so every current patch target
becomes invalid. Required Knapsack behavior should move to a supported plugin,
Gateway client, configuration, or a deterministic source-level patch step.
The upgrade must not reintroduce manual edits to generated `dist` chunks.

### Verified requester-aware MCP seam

OpenClaw `2026.8.2` exposes
`api.registerMcpServerConnectionResolver(...)`. Its resolver receives only
host-provided identity fields:

- `requesterSenderId` (required);
- `agentAccountId` (optional); and
- `messageChannel` (optional).

The runtime omits requester-scoped servers when the sender id is absent, calls
the resolver with the trusted Slack sender/account/channel when it is present,
redacts resolved URLs and headers, and revalidates an active connection at
least every five minutes. An isolated runtime test confirmed that an empty
sender fails closed and `U0ASEDSQP8F`/`bankaya`/`slack` reaches the resolver
unchanged.

This is the supported replacement direction for Knapsack's compiled
`_knapsack_session_id` and Slack-identity tool-argument injection. It is not a
drop-in replacement yet:

1. The resolver returns an HTTP URL and headers, while Knapsack's current
   Studio and Snowflake bridges are local stdio subprocesses.
2. It does not expose OpenClaw's internal session id, scope key, or Slack
   workspace id. The local broker must authorize the trusted tuple
   `(messageChannel, agentAccountId, requesterSenderId)` directly and map the
   configured account to its workspace without guessing among active users.
3. Registering a resolver makes that server requester-scoped for every turn.
   The Desktop/webchat path must be proven to receive a trusted synthetic
   requester identity, or Knapsack must expose a separate explicitly local
   transport without weakening the channel path.

The implementation PR should therefore add a loopback HTTP MCP bridge owned by
Tauri and a bundled Knapsack plugin that resolves `studio` and `snowflake` to
that bridge with an app-authenticated capability. Tests must cover
two simultaneous Slack users, two Slack workspaces with colliding user ids,
Desktop chat, missing identity, revoked identity, header redaction, and runtime
revalidation before the compiled patches are removed.

### Draft implementation status

The stacked implementation draft adds the supported bridge without changing
the bundled runtime or removing the legacy stdio MCP servers:

- the plugin is enabled only when the exact bundled OpenClaw version is
  `2026.8.2` or newer and removes only its own config on rollback;
- the resolver forwards the host-supplied sender, account and channel through
  an authenticated loopback HTTP endpoint;
- Slack authorization verifies the exact configured bot account and sender
  through Slack before deriving the Studio email, so it never selects from the
  global active-session set; and
- unknown channels, missing senders, invalid headers and service-account domain
  mismatches fail closed.

The draft is intentionally not merge-ready yet. OpenClaw `2026.8.2` does not
accept a requester sender on the `agent` RPC currently used by Desktop chat.
The Desktop path must either move to a gateway method that supplies a trusted
client identity or gain an upstream supported identity field, and an isolated
8.2 runtime must prove that value reaches the resolver. Until then, the current
`2026.5.22` runtime and legacy stdio bridges remain the active production path.

## New capabilities that align with Knapsack

These should be adopted only after the compatibility runtime is stable:

1. Per-requester MCP OAuth and private credential prompts for inline Studio
   connector setup.
2. Managed browser cookie import for Chrome-family profiles.
3. Durable meeting transcripts, summaries, progress cards and attachments.
4. A2A and bounded multi-agent execution with loop protection.
5. Live model discovery and explicit model policies.
6. External Gateway supervision owned by the Tauri application.
7. Structured questions and interactive chat widgets.

## Defaults to override before any shared-user test

- Disable dreaming explicitly.
- Disable autonomous self-learning explicitly.
- Disable cross-conversation recall unless it is demonstrably scoped to the
  intended Knapsack user and agent.
- Preserve `per-account-channel-peer` direct-message isolation and self-only
  session visibility.
- Keep connector authorization tied to a verified requester rather than merely
  to the selected conversation.
- Set explicit concurrency and multi-agent turn budgets.
- Use external supervisor mode so OpenClaw and Tauri do not compete over
  Gateway restarts or updates.

## Proposed pull-request sequence

1. **Runtime prerequisites**: Node 22.22.3, hermetic smoke-test overrides,
   dependency-lock generation, and migration fixtures. No OpenClaw swap.
2. **Runtime rebase**: vendor `2026.8.2`, port required Knapsack boundaries,
   remove obsolete compiled patches, and pass bundle/package tests.
3. **Shared-user security validation**: Slack identity, Studio/Snowflake,
   simultaneous accounts, session isolation, and connector authorization.
4. **Product adoption**: browser import, inline connector credentials, meeting
   context, model discovery, and bounded multi-agent collaboration.

No pull request in this sequence should merge until Codex, Vercel, GitHub CI,
macOS, and Windows findings have been reviewed and addressed. No release should
be created by the compatibility spike.

## Release gate

Before production, validate all of the following using copied or synthetic
state first, followed by a dedicated dev build:

- clean install and upgrade from the current production version;
- config and session migration with rollback;
- Gateway startup, restart, updater and relaunch;
- browser navigation, tabs, login import and downloads;
- Slack/Telegram/WhatsApp routing and attachments;
- requester-correct Gmail, Drive, Calendar, Studio and Snowflake access;
- meeting recording through transcript, notes, brief and meeting chat;
- agent creation/deletion and bounded multi-agent chat;
- macOS Intel/Apple Silicon and Windows packaging;
- explicit proof that the installed production app still uses the intended
  runtime, Node binary and migrated state.
