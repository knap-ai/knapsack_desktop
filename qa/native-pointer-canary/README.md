# Operator-independent WKWebView pointer canary

This separate AppKit target tests whether the clean hosted macOS runner can deliver real XCTest pointer input through WKWebView. It is not Knapsack and does not prove product search navigation. It imports no product source, serves no ports, reads no account state and has no network entitlement. The existing human-gated native fixture is unchanged.

The PR-only job checks out the immutable PR head with persisted credentials disabled, contents-read permission, no signing secrets and no privileged triggers. It requires the standard GitHub-hosted macos-26 arm64 image and Xcode 26.6 at its fixed installed path. Missing prerequisites refuse execution; nothing installs or changes permissions, Automation Mode, TCC or security policy. The pinned checkout/upload actions are the only external actions.

`python3 -m unittest discover -s qa/native-pointer-canary -p 'test_*.py' -v` runs portable project-generation, source-contract and refusal tests. `python3 qa/native-pointer-canary/run.py` refuses a local or self-hosted machine. Only the hosted job builds/tests; the application is ad-hoc signed, sandboxed and uses nonpersistent WebKit storage under a private disposable build root. The test runner uses ordinary XCTest UI automation. The script verifies the app's identity, ad-hoc signature and network-denying sandbox before launch.

XCTest launches only the exact generated app URL, checks bundle ID, foreground and hittability, then uses XCUICoordinate clicks. Both synthetic Meeting and Library must emit nonce-bound trusted primary down/up/click sequences while the native window is visible/key and active, and their synthetic destination text must appear. Keyboard/programmatic activation cannot satisfy the trusted pointer receipt. There is no automatic click of any human Start gate. The app independently exits after 100 seconds; XCTest terminates its exact app on completion. Build/test commands and the overall job are bounded. Timeout cleanup targets only the newly created xcodebuild process group, never a process-name match.

Outcome JSON is now derived from structured XCTest attachments and xcresult, not a runner-written marker. The UI test never writes RUNNER_TEMP. Exactly one passing test in the expected UI bundle/suite, no skips/expected failures, and all five named nonce-bound setup/render/Meeting/Library/completion attachments are required. Both pointer attachments must contain the native trusted receipt and checked destination. Wrong suite, stale nonce, missing/duplicate attachments, path escapes, failure or nonzero exit refuse a pass. A collected failed test (including setup failure after foreground) is `test_failure`; absent host prerequisites or no executed test is `unavailable`. All non-pass outcomes fail CI. Synthetic build/test logs, parsed results and attachments are retained for seven days.

The first hosted run compiled and launched the disposable app, reached a foreground/hittable window, then failed before clicks: the UI runner could not write its old RUNNER_TEMP marker (NSCocoa 513/EPERM). That was a test-tooling error, incorrectly classified as unavailable. This change uses XCTest-owned attachment persistence without changing sandbox or OS permissions. The second run reached the foreground window and emitted setup evidence but found an empty WebView accessibility Group before any click. It lacked finite document-load diagnostics, so an exact native cause was not proven. The prior about:blank-only allowlist could cancel an initial in-memory navigation whose URL differs or is absent; that hypothesis is not a native pass. The fixture is now a bundled local HTML resource with exact-file-only navigation, no query/fragment or alternate file/remote navigation, and unchanged CSP. Native loading/document-ready/navigation-finished/ready/failure stages separate document loading from subsequent button accessibility. A render attachment records the observed state. The parser accepts only fixed phases with the observed optional numeric-index/UUID export suffix, and still verifies manifest/test/nonce/content. Thirteen portable refusal/parser tests and Swift parsing pass; the revised hosted pointer result remains unverified.

After a canary pass, a separate reviewed product fixture is still needed to mount the exact combined candidate's real MeetingNotesMode and owner-scoped Library destination and exercise search dismissal/drag/secondary-click behavior. Canary success must never be relabeled as that product acceptance.

API references: [XCUIApplication](https://developer.apple.com/documentation/xcuiautomation/xcuiapplication), [runner image inventory](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md). Runner inventory is feasibility evidence only; the exact job result decides availability.
